## 残タスク

**残っているのは Phase B3（下の 3.）と、4. の末尾に挙げた「やらなかったもの」だけ。**

### 1. 出発前に直したい UI の不具合 2 件 → **どちらも 2026-08-11 に修正済み**

**(a) `.tbtn` の `display` が `hidden` 属性に勝っていた。** 「お土産を追加」「区分を追加」が
編集モードの外でも表示されていた。`assets/css/controls.css` に
`.tbtn[hidden] { display: none; }` を足して解消（`.syncbar` / `.pubpanel` / `.pubstat` と
同じ打ち消し）。**本番のページで「区分を追加」「お土産を追加」がどちらも
出ていないことを確認済み**（持ち物側は Phase B2 からずっと出ていた）。

**(b) チェックボックスの縦位置。** **`align-items` だけが原因ではなかった。**
上揃えにするだけでは直らず、今度はチェックが名前より 13.1px 上へ浮く。真因は
`.svitem__line` / `.svitem__note` が `<p>` で、`base.css` に `p` のリセットが無いため
**UA 既定の `margin: 1em 0`（14px）が効いていた**こと。

その場は `.svitem__body p { margin: 0 }` で塞いだが、**同じ罠は他の場所にもあった**
（`.pkitem__line` / `.pubpanel__state` / `.syncbar__msg` が各自で `margin: 0` を書いて
回避しており、書き忘れた 1 か所だけが壊れる形になっていた）ので、
PR #13 で `base.css` に `p { margin: 0 }` を入れ、souvenirs 側の打ち消しは消した。
**本番のお土産ページで、メモを持つ行も含めて全行のずれが 0.9px であることを確認済み。**
残っている差（編集モードの 1 行では 7.5px 上に付く）は設計書 §13。

### 2. Phase B3（コメント）── 着手は帰国後を勧める

設計書 §4.3 / §7.5。`event:<id>` / `day:<n>` / `packing:<id>` / `global` の 4 対象。

**出発前日に始めないほうがよい理由が 2 つある。** 4 か所すべて（予定シート・日付ヘッダー・
持ち物の行・旅程ページ）に手を入れるので、いま動いている 3 ページ全部を触ることになる。
それに、予定・持ち物・お土産にはすでに `note` 欄があり、B3 が足すのは「誰が・いつ」と
「1 対象に複数件」だけ ── 旅行中に本当に要るかは、使ってみないと分からない。

共通部品（`page-notice.js` / `focus-key.js` / `row-controls.js`）は B5 で揃えたので、
4 本目は写さずに書ける。`assets/js/souvenirs.js` の `createSync()` / `createPublishUI()` の
呼び出しをそのまま写すこと（注入口は 6 つ、`content` は組で渡す）。

**PR #13 で、B3 が踏むはずだった罠は先に潰してある:**

- `noun` の二重渡し（片方だけ書き換えると同期バーとステータスが違う名前を出す）は、
  `sync` が `noun` を公開して `publish-ui` が突き合わせる形にした。**違えば組み立ての
  時点で落ちる**ので、B3 が写し間違えても黙って通ることは無い
- `validateEvent()` は `{field, message}` を返す。`comments-validate.js` を書くときは
  この形に合わせること
- `tokens.test.js` の色リテラル検査は `assets/css/` の走査で対象を決めるので、
  `comments.css` を足しても**テスト側に足す作業は要らない**
- `base.css` が `p` を初期化したので、`<p>` を並べても UA の 1em は付いてこない

### 3. 設計書 §13 の繰り越し → **2026-08-11 に PR #13 で大半を解消**

B5 の時点で 10 件を carry としていたが、そのうち UI の 2 件は上の「1.」で、
残りは PR #13 でまとめて片付けた。**テストは 567 → 611。**

主なもの:

- **検証を通らないリモートを 409 で塞がなくなった。** 逃げ道の「取り込む」も同じ検証で
  落ちるので、その端末では直せない袋小路だった
- **時計ずれによる上書き**を、リモート本文の指紋（`assets/js/fingerprint.js`）で塞いだ。
  時計を一切見ない。`tp:<name>-base` を置き換えるのではなく**足した**ので、
  起動時の判断は今も `updatedAt` のまま
- 保存領域に書けない端末の毎回 409 / 控えを書けなかった公開のコミット URL /
  取り込みが `base` だけ失敗したときの巻き戻り / 「取り込む」ボタンの構えっぱなし
- 地図の `fitBounds`（内容だけの編集で視点が巻き戻っていた）/ `imagePos` の許可リスト /
  シートを閉じると未保存の入力が黙って消える件 / `aria-invalid` を不備のある欄すべてに

**指紋の移行は本番で 1 回通した（2026-08-11）。** 持ち物リストの内容を直して公開した
コミット [`4bb4357`](https://github.com/y-shinozaki/travel-plans/commit/4bb4357) が、
まさにその 1 回目にあたる:

- 公開前: `tp:packing-fp` は **無し**、`tp:packing-base` は有り
  → 設計どおり「指紋を持たない端末は従来どおり `updatedAt` で判断」に落ちた
- **409 は出ず、1 回で通った**
- 公開後: `tp:packing-fp` に指紋が入り、`base` も更新された。以降この端末は指紋で判定される

**旅程とお土産はまだ指紋を持っていない。** それぞれ最初の公開で同じ経路を 1 回通る
（持ち物と同じ結果になるはず）。**もし 409 が出たら、「取り込む」を 1 回押してから
公開し直せばよい** ── それで指紋が入り、以降は出なくなる。

指紋は端末ごと・ファイルごとに入る。**他の 5 人の端末も、それぞれ最初の公開のときに
同じ 1 回を通る**（閲覧しかしない端末には関係ない）。

**やらなかったもの**（理由つきで設計書 §13 に残してある）:

- **画像の外部ホスト直リンク** ── `events.json` が暗号文で、URL の張り替えは画面からしか
  できない。24 件の画像を自前配置するには全イベントを編集し直すことになる
- **公開ボタンの件数表示** ── 取り込んだ本文を持つ 3 つ目のキーが要る
- **`sheet.open()` の Node 対応は器だけ** ── `event-editor.js` は今も文字列を渡している。
  移すのは B3 の作業と一緒でよい
- `.ev` の padding のはみ出し（実データでは発生しない）/ 呼び出し側のない CSS /
  `createMap`・`createSheet` の本体テスト（実 DOM と Leaflet が要る）

## 今日わかった、次に効くこと

**エントリポイントと CSS の組み合わせは、読んで判定せずにブラウザで開いて確かめること。**

(a) の不具合は、Phase B5 の全工程 ── 9 タスク、レビュー 4 回、最終の全体レビュー ──
を素通りした。`node --test` は CSS の詳細度勝負を見られず、レビューは JS だけを読んで
「隠れている」と判定した。さらに悪いことに、**その判定を信じて確認手順を
「ボタンは表示されない」と書き換えてしまった**（もとの記述のほうが実態に合っていた）。

実際にページを開いた 30 秒で見つかっている。`souvenirs.js` / `packing.js` /
`schedule.js` はテストを持たない規約なので、**ここだけは人かブラウザが見るしかない。**

**同じ日に、同じ形の見落としがあと 2 つ出た。**

1. **設計書に書いた「直し方」自体も、実測するまで信用しないこと。** §13 は (b) を
   「`align-items: flex-start` にすればよい」と記録していたが、そのとおりにしても
   直らなかった ── ずれる向きが下から上へ変わるだけだった。読んで判定した記録は、
   直し方の側にも残る
2. **テストのスタブは、実 DOM と違うところで嘘をつく。** PR #13 で足した「未保存の
   入力を捨てない」仕組みは、スナップショットを `sheet.open()` より**前**で撮っていて、
   触っていないフォームまで閉じるのを断っていた。**テストは 609 件通っていた** ──
   スタブの本文は `open` の前から入力欄を持っているので、この順序の誤りを再現できない。
   これも実ページを開いて見つかった

**合言葉が要って実ページを開けないときは、使い捨ての合言葉で暗号化したデータを
別オリジンに置けばよい**（PR #13 ではそうやって旅程・持ち物・お土産の全ページを
実際に動かして確かめた）。本物の合言葉も本物のデータも要らない。
