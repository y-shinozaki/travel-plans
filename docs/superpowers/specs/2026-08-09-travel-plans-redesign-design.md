## 1. 目的

5 つの要求を満たすためにアプリを再構成する。

1. 別のデザイン仕様で見た目を刷新する
2. 二人分のチェックボックス付き持ち物リストを作る
3. 要所にコメントを残せるようにする
4. Gmail と LINE の情報を JSON に格納し、Pages から検索できるようにする
5. 検索画面へはパスワード入力で遷移する

検討の過程で、2 と 4 に付随して次が追加された。

6. 持ち物リストはユーザーが項目・区分を追加／修正／削除／並べ替えできる
7. カレンダーの予定も同様に追加／修正／削除できる
8. 編集結果を UI の操作だけで同行者に共有できる

**2026-08-09 に 4 と 5 の扱いが変わった。**（当初の要求として記録のために残してある。）

- **4 は取り下げた。** Gmail / LINE の中身は、検索できるようにするのではなく、
  人が読んで旅程へ反映する一度きりの作業として済ませた（§2.3）
- **5 は残るが意味が変わった。** パスワードは「検索画面への遷移を制限するもの」ではなく、
  同期する JSON 全部を復号する鍵になった（§6.1）

### 3.5 アイコン

アイコンフォントは使わない。単一のインライン SVG スプライト（`<symbol>` 約 30 個）を
`icons.js` が各ページに注入し、`<use href="#i-xxx">` で参照する。

- 線幅 1.0〜1.4px。1px ヘアラインと太さを揃える
- `stroke: currentColor` で色を継承
- 追加ネットワークリクエストなし

### 3.6 モーション

| 対象 | 内容 |
|---|---|
| 見出し | 行マスクからせり上がる（1.05s） |
| セクション | フェード＋22px 上昇。並列要素は 0.08〜0.12s ずつ時差 |
| 主要画像 | `scale(1.1) → 1` のスローズーム（2.4〜2.6s） |
| ボタン | 地色が右へ抜ける＋アイコンが 5px 進む |
| チェックボックス | パスを `stroke-dashoffset` で 0.42s かけて描画 |
| カレンダー | イベントを 12ms 刻みで順に出現 |
| 一覧行 | ホバーで左に せり出し、画像が 1.08 倍＋彩度回復 |
| イージング | `cubic-bezier(.22, 1, .36, 1)` |

`prefers-reduced-motion: reduce` で全アニメーションを無効化する。

**スクロール連動の実装上の注意**: IntersectionObserver 単体では、アンカージャンプや
スクロール位置復元で要素をまたいだときに `is-in` が付かず、コンテンツが `opacity: 0` の
まま残る。`threshold: 0` に加えて、スクロール時に「ビューポート下端より上に来た未表示要素を
無条件で表示する」掃引処理を併用する。

また `reveal`（フェード）と `drawline`（罫線を引く）を同一要素に付けてはならない。
CSS の `animation` プロパティが後勝ちで上書きされ、要素が不可視のまま残る。

## 4. データモデル

すべて JSON。置き場所は 3 種類で、書き換える主体はいずれもユーザー（UI）。

| データ | リモート（正） | ローカル |
|---|---|---|
| 旅程 | `assets/data/events.json` | `localStorage["tp:events"]` |
| 持ち物 | `assets/data/packing.json` | `localStorage["tp:packing"]` |
| コメント | `assets/data/comments.json` | `localStorage["tp:comments"]` |

（Gmail / LINE の `archive.enc` は取りやめた。§2.3・§4.4）

すべてのファイルはオブジェクトを最上位に置き、`updatedAt`（ISO8601）を持つ。
配列を最上位にしない。版の比較に必要なため。

**B4 以降、リモートに置かれるのは暗号文**（§6）。上の「リモート（正）」はパスの話であって、
中身が平文だという意味ではない。

**ローカルの下書きは平文のまま置く**（2026-08-10 決定）。暗号化すると、鍵を失った端末は
リモートも手元の未公開の編集も両方読めなくなる。下書きは公開前の作業中の値なので、
救い出せる状態で残しておくほうが得るものが大きい。`localStorage` には既に
公開用トークンも導出鍵も平文で入っており（§5.4・§6.3）、下書きだけ暗号化しても
その端末の秘匿性は上がらない。

### 4.1 旅程（events.json）

旅行日の配列 `days` も同じファイルに置く。`startDay` / `endDay` はこの配列の添字であり、
別ファイルに分けると添字がずれたときに壊れるため。

```jsonc
{
  "updatedAt": "2026-08-09T10:00:00+09:00",
  "days": [
    { "dow": "水", "date": "8/12" },
    { "dow": "木", "date": "8/13" }
    // ... 6 日分
  ],
  "events": [ /* 下記のイベント */ ]
}
```

イベント 1 件の形:

```jsonc
{
  "id": "ev-3",
  "cat": "cat-hotel",              // cat-move | cat-sight | cat-food | cat-hotel | cat-shop
  "title": "バンコクホテル",
  "allDay": false,
  "startDay": 0,                   // days[] のインデックス
  "endDay": 2,                     // startDay と異なれば日をまたぐ
  "start": 15.0,                   // 10進時間。allDay のときは持たない
  "end": 11.0,
  "location": "137 ピラーズ レジデンス バンコク",
  "lat": 13.7278,
  "lng": 100.5601,
  "url": "",
  "notes": "",
  "image": ""
}
```

- 旧形式の `d`（単日）と `multiDay` は廃止し、常に `startDay` / `endDay` を持つ
- 表示用の `time` 文字列（`"10:35 → 15:05"`）は**保持しない**。`start` / `end` から生成する。
  二重管理はずれるため
- `lat` と `lng` は両方揃ったときのみ地図にピンを立てる。片方だけなら座標なしとして扱う

日をまたぐイベントは `expandEvents()` が日ごとのセグメントに割って描画する。
実体は 1 件なので、削除すると全セグメントが消える。

```
startDay: start 〜 24 / 中間日: 0 〜 24 / endDay: 0 〜 end
```

### 4.2 持ち物リスト（packing.json）

```jsonc
{
  "updatedAt": "2026-08-09T10:00:00+09:00",
  "members": { "a": "Yuichi", "b": "Partner" },
  "groups": [
    {
      "id": "g-valuables",
      "name": "貴重品・書類",
      "icon": "i-key",
      "items": [
        { "id": "passport", "name": "パスポート", "note": "残存6か月以上",
          "a": true, "b": true }
      ]
    }
  ]
}
```

`a` / `b` は二人分のチェック状態。区分・項目とも追加／改名／削除／並べ替えができ、
項目は区分をまたいで移動できる。

### 4.3 コメント（comments.json）

対象キーと本文だけを持つ単純な構造。1 つのモジュールで 4 か所の要件を満たす。

```jsonc
{
  "updatedAt": "2026-08-09T10:00:00+09:00",
  "byTarget": {
    "event:ev-3":      [{ "id": "c1", "who": "Yuichi",
                          "at": "2026-08-04T07:55:00+09:00",
                          "text": "渡し船は 5B。" }],
    "day:1":           [],
    "packing:adapter": [],
    "global":          []
  }
}
```

コメントも公開対象とする。「この店は予約済み」のような内容は同行者と共有する価値が
あるため。個人メモに留めたい要求が出た場合は、公開しない `private` 種別を足す。

## 5. 保存と共有

### 5.1 方針

- リモートの JSON が**正**
- 編集は即座に localStorage へ入る（下書き）
- 「公開」を押すと GitHub Contents API 経由でリモートへコミットされる
- 同行者はページを開くだけで最新を受け取る

トークンを持つ端末（Yuichi）だけが公開でき、持たない端末は閲覧と下書き編集のみ。
役割が自然に分かれる。

**B4 以降、この流れに暗号化が挟まる**（§6）。読み込みは fetch → **復号** → 検証 → 表示、
公開は 検証 → **暗号化** → PUT。順序を守ること ── 検証の前に復号しないと検証器が
暗号文を見ることになり、暗号化の前に検証しないと壊れたデータがリポジトリに入る。

暗号は `crypto.js` の codec に閉じ込め、`createSync()` へ注入する。**注入口は
`draftKey` / `baseKey` / `validate` / `commitMessage` / `codec` の 5 つを一度に足す**
── §13 の「3 つのうち一部だけを注入可能にすると旅程の下書きが黙って消える」に
codec が加わっただけで、危険の性質は同じ。既定値は現在の挙動（`events` /
`events-base` / `validateEvents` / 今のコミットメッセージ / 素通しの codec）。

### 5.2 読み込み時の流れ

各 JSON はトップレベルに `updatedAt` を持つ。localStorage には取り込んだ時点の
`baseUpdatedAt` を併せて保存する。

**B4 以降は fetch のあとに復号が挟まる。** 起動順も変わり、
**鍵の確認 → `publish-ui` の組み立て → `load()`** になる（§6.5）。
これは元々「`load()` が先で、投げるとトークン設定も公開ボタンも DOM に現れない」
という順序だったのを直したもの。詳しい経緯と残った穴は §13 の
「`sync.load()` が投げるとトークン設定への導線も出ない（B4 で解消）」を参照。

```
リモートを fetch → codec.decode()（ct が無ければ平文として素通し）
  ├ ローカルなし                       → リモートを取り込む
  ├ remote.updatedAt == baseUpdatedAt  → ローカルを使う
  ├ remote が新しく、ローカルに未公開の変更なし → 静かにリモートへ更新
  └ remote が新しく、ローカルに未公開の変更あり
        → 画面上部にバーを出す
          「新しい版があります ／ 取り込む ・ 自分の変更を残す」
```

**リモートで黙って上書きしない。** 同行者が手元で付けたチェックを失わせないため、
取り込みは必ず明示操作にする。

fetch が失敗した場合（オフライン、Pages 障害）はローカルのデータで動作を継続し、
「最新の確認ができませんでした」とだけ表示する。機能は落とさない。

### 5.3 公開の流れ

GitHub Contents API を使う。

```
1. 検証。validateEvents を通らなければここで止める（壊れたものを push しない）
2. updatedAt を現在時刻に更新
3. codec.encode() で封筒にする ← B4 から。IV を引き直す（§6.2）
4. GET  /repos/{owner}/{repo}/contents/assets/data/events.json  → sha と本文
5. 本文の updatedAt を baseUpdatedAt と比較する ← 競合検出はここ
     進んでいれば「取り込んでから公開し直してください」で中断する
6. PUT  同 URL  { message, content: base64(JSON), sha }
7. 成功 → baseUpdatedAt を更新、「公開しました」を表示
```

手順 5 が読むのは**封筒の外側の** `updatedAt`、手順 7 が `baseUpdatedAt` に入れるのは
**内側の** `updatedAt`。`encode` が両方に同じ値を書くので一致する（§6.2）。

注意点:

- **base64 化に `btoa()` を直接使わない**。日本語を含む UTF-8 は例外になる。
  `TextEncoder` でバイト列にしてから base64 化する
- **競合検出を sha に頼らないこと。** GET の直後に PUT するので sha はほぼ常に最新で、
  409 が返るのは GET と PUT の間の数十ミリ秒に別の公開が挟まった場合だけ。
  現実の競合は「B がページを開いて 30 分編集する間に A が公開する」という形で起きる。
  この場合 sha は新しいままなので **PUT は成功し、A の作業が黙って消える**。
  手順 3 の `updatedAt` 比較が本当の砦であり、GET が返す本文を捨ててはならない。
  409 の処理は残すが、それは最後の保険であって主たる検出手段ではない
  （2026-08-09、Task 7 のレビューで判明。当初この節は sha 競合を主たる検出手段と書いていた）
- ページ起動時の `decideSync` はページを開いた瞬間しか見ないので、
  開いたまま編集している間に起きた公開は検出できない。公開時にもう一度確かめる必要がある
- Pages への反映には 1 分程度かかる。公開直後に「反映まで少し時間がかかります」と添える
- 公開は 3 つの JSON をまとめてではなく、変更のあったファイルのみ

### 5.4 トークンの扱い

- **fine-grained personal access token** を使う
- 権限は本リポジトリの **Contents: Read and write のみ**。他のリポジトリ・他の権限は与えない
- 有効期限を設定する（旅行終了後まで）
- コードにもリポジトリにも書かない。UI から一度入力し、`localStorage["tp:gh-token"]` に保存
- 「トークンを削除」操作を設定画面に置く
- トークン未設定の端末では「公開」ボタン自体を出さない

### 5.5 CDN 依存の排除

（2026-08-09 の見直しで §6.4 からここへ移した。中身は**トークンの置き場所に付随する
判断**であって、認証とも暗号化とも関係がない。§6 の下に置いたままだと、
検索アーカイブを畳むときに巻き添えで消える。）

**書き込み権限を持つトークンをブラウザに置く以上、外部 CDN の JS を無条件に読み込むのは
危険。** unpkg 上の Leaflet が改竄された場合、トークンを外部へ送ることも、
リポジトリへ任意の内容を push することもできる。

対策として **Leaflet を `assets/vendor/leaflet/` に自前で配置する**。
Google Fonts は CSS とフォントのみでスクリプトを実行しないため継続利用してよいが、
可能なら同様にセルフホストする。

## 6. 認証と暗号化

### 6.1 合言葉の役割は復号鍵ひとつ

合言葉は**同期する JSON を復号する鍵**であり、それだけである。

当初はこれに「`index.html` からの遷移を制限する目隠し」という第 2 の役割を持たせていたが、
**目隠しは静的サイトでは成立しない。** GitHub Pages は誰でも URL を開けるので、
`assets/data/events.json` を直接叩けば JS のパスワード判定を通らずに中身が読める。
遷移ガード（§6.3）は再入力の手間を省くための導線であって、防御ではない。

そのうえで、**暗号化はやめない。** 暗号化だけをやめて合言葉を残すのが最悪の選択で、
守られていないものを守られているように見せてしまい、その前提で機微な情報
（予約番号、同行者の連絡先など）を書き足すことになる。

暗号化の対象は**同期する JSON 全部** ── `events.json` / `packing.json` / `comments.json`。
検索アーカイブ（旧 §4.4）の専用措置ではない。

**合言葉を忘れると復旧できない。** git 履歴に残るのも暗号文なので、リポジトリからも戻せない。
`localStorage` の導出鍵（§6.3）はブラウザのデータを消せば一緒に消える。

したがって **B4 の実装時に「合言葉そのものをパスワードマネージャ等に控える」ことを
利用者へ伝える。** 旅程の平文の控え（紙・PDF）は持たない方針なので
（2026-08-10 決定）、合言葉の控えが唯一の保険になる。

### 6.2 暗号仕様 — 封筒 JSON

| 項目 | 内容 |
|---|---|
| 鍵導出 | PBKDF2-HMAC-SHA256、反復 600,000 回、ソルト 16 バイト（乱数） |
| 暗号 | AES-GCM 256bit、IV 12 バイト（乱数）。**IV は公開のたびに引き直す** |
| ファイル構造 | 下記の封筒 JSON |

```jsonc
{
  "updatedAt": "2026-08-10T12:00:00.000Z",   // 暗号文の外。突き合わせ用の複製
  "kdf": { "salt": "<base64>", "iter": 600000 },
  "iv": "<base64>",
  "ct": "<base64>"                            // ここに JSON 本体が入る
}
```

**当初は `"TPENC1"(6) + salt(16) + iv(12) + ciphertext` の生バイト列と決めていたが、
2026-08-10 に封筒 JSON へ変更した。理由は B1 の競合検出が壊れるため。**
`sync.js` の `assertRemoteNotAhead()` は GET した本文を `JSON.parse` して `updatedAt` を
読む。中身が不透明なバイト列だと読めず、`conflictChecked: false` を返して
**突き合わせを省いたまま公開が通る** ── B1 の最終レビューが「sha では捕まらない
現実の競合」に対して作り込んだ唯一のガードが、常時オフになる。

封筒にすれば `fetchRemote()` も `stampOf()` も `assertRemoteNotAhead()` も無改造で動く。
**外に出るのは「いつ最後に直したか」だけで、行き先も時刻も宿も暗号文の中にある。**

**外側の `updatedAt` は認証されない。** AES-GCM の認証タグが守るのは `ct` だけなので、
外側は改竄・破損を検知できない。よって**復号後に内側の `updatedAt` と突き合わせ、
食い違えば内側を正とし、その旨を画面に出す**。外側はあくまで突き合わせ用の複製である。

`ct` を持たない値は**平文とみなして素通しする**。これが切り替え当日の移行経路になる（§6.5）。

合言葉が違えば GCM の認証タグ検証が失敗する。ただし**「合言葉が違う」と
「暗号文が壊れている」は GCM からは区別できない**ので、封筒の `kdf` が手元の鍵素材と
一致するかで見分ける（§9）。暗号化・復号は WebCrypto でブラウザ上のみ。

### 6.3 鍵の保存と一生

**導出した鍵は `localStorage`（`tp:key`）に保存する。**

```
1. index.html で合言葉を入力
2. events.json を取得し、封筒に kdf があればそのソルトを、
   無ければ（＝まだ平文）新しいソルトを生成する
3. PBKDF2 600,000 回で導出 → tp:key に { salt, iter, key } を保存
4. 以降のページは鍵の有無を見るだけ。PBKDF2 はこの端末でもう走らない
5. 封筒の kdf がキャッシュと違えば、その鍵では復号できない
   → index.html へ戻して再入力させる
```

**`sessionStorage` ではなく `localStorage` にしたのは 2026-08-10 の決定**（当初は
`sessionStorage`）。タブを閉じるたびに再入力になると、旅行中の現地で
「合言葉を忘れた／入力できない」が起きやすい。代わりに**端末を拾われたときの防御は
落ちる**が、守りたいのは「URL を知られても中身が読めないこと」であって端末の盗難ではない。
公開用トークン（`tp:gh-token`）が既に平文で `localStorage` にあるのと同じ判断。

**ソルトは 3 つの JSON で共有する。** codec はファイルの `kdf` からではなく
**キャッシュした鍵素材から**組み立てる。ファイルごとにソルトを引くと、
`packing.json` を足した時点で `events.json` と別の鍵になり、
**ページを移動するたびに 1〜3 秒の再導出が挟まる**。

各ページの先頭で鍵の有無を確認し、無ければ `index.html` へ戻す。
**このリダイレクトは防御ではない**（§6.1）。鍵が無ければ JSON を復号できないという
一点だけが防御で、遷移ガードはその手前の案内にすぎない。

### 6.4 §5 へ移動

CDN 依存の排除は §5.5 へ移した。節番号は参照を保つために残してある。

### 6.5 平文からの移行と、復旧手段が 1 本になること

**移行はコミット 1 つで済む。** 自分の端末でページを開き（今の平文が読める）、
合言葉を設定し、「公開」を押す。`encode` が封筒を作って PUT するので、
それだけで `events.json` が暗号文になる。移行スクリプトも CLI も要らない。

**この 1 回だけは順序が重要。** 押した瞬間から鍵の無い端末は旅程を見られなくなるので、
先に合言葉を決め、同行者へ配る算段を付けてから押すこと。

**手編集の経路は廃止する**（2026-08-10 決定）。`CLAUDE.md` は「`events.json` を手で編集して
commit する」を正規手順として案内してきたが、暗号化後はテキストエディタで開けない。
暗号化・復号の CLI は作らない。

その結果、**リモートが壊れたときの復旧手段は「正しい下書きを持つ端末から公開し直す」
1 本だけになる。** だから §13 の繰り越し「`sync.load()` が投げるとトークン設定への
導線も出ない」は B4 の必須項目だった ── `publish-ui` を `load()` より前に組み立てないと、
画面が起動しない壊れ方をしたときに**復旧手段がゼロ**になる（従来はそこに
git コミットという逃げ道があった）。**2026-08-10: 実装済み。** 経緯と残った穴は
§13 の同項目を参照。

### 7.3 packing.html

- 二人分の進捗（達成数と細いバー）
- 表は「区分 → 項目」の 2 階層
- 通常時は読むだけの静かな見た目。「リストを編集」で編集モードへ

**編集モードでできること**

| 操作 | 手段 |
|---|---|
| 項目の追加 | 区分ごとの「項目を追加」。追加後は入力欄にフォーカス |
| 区分の追加 | 表の最下部 |
| 名称・メモの編集 | 行がそのまま入力欄になる |
| 並べ替え | ドラッグハンドル、または ↑↓ ボタン |
| 区分をまたぐ移動 | ドラッグ、または ↑↓ で端に達したとき隣の区分へ送る |
| 削除 | ✕ を 2 度押し。区分は「4件ごと削除」と中身の数を出す |

**ドラッグは Pointer Events で実装する。** HTML5 Drag & Drop はタッチ端末で動作しない。
ハンドルに `touch-action: none` を付け、スクロールとの競合を避ける。
`pointermove` / `pointerup` は**ハンドルではなく `window`** に登録する。
`setPointerCapture` が失敗する環境で、ポインタがハンドルから外れた瞬間に
ドラッグが止まるため。capture は補助として `try/catch` で囲む。

並び順は DOM を正として、指を離した時点で `data-id` を読んで配列を再構築する。
ドラッグ中に再描画しないので動きが途切れない。

ドラッグが使えない環境のために ↑↓ ボタンを常に併設する。

### 7.5 コメント

## 9. エラー処理の方針

- **ブラウザの `alert` / `confirm` / `prompt` を使わない。** ページ全体をブロックするため。
  破壊的操作は「2 度押し」で確定させ、エラーはインラインに表示する
- 失敗を握りつぶさない。fetch 失敗、復号失敗、公開の 409、JSON の不正はすべて
  画面に理由を出す
- リモート取得に失敗しても、ローカルデータでの動作は継続する
- **鍵と合言葉は DOM にも例外文にも出さない**（`token.js` と同じ規約。§5.4）

**B4 で足す復号系の見分け**（`schedule.js` の `catch` は今 4 通りに分けている）:

| 状態 | 見分け方 | 画面 |
|---|---|---|
| 鍵が無い | 鍵のキャッシュが空 | `index.html` へ戻す（`load()` より前に判定する） |
| 別の合言葉で暗号化されている | 封筒の `kdf` が手元の鍵素材と不一致 | 「別の合言葉で暗号化されています」＋再入力への導線 |
| 復号に失敗した | `kdf` は一致するが GCM の認証タグ検証が失敗 | 「データが壊れています」（合言葉は合っている見込み） |
| 内側と外側の `updatedAt` が食い違う | `decode` が返す警告 | 内側を正として表示し、その旨を出す |

GCM は「合言葉が違う」と「暗号文が壊れている」を区別できない。`kdf` の一致で
上の 2 行に分けているのはそのためで、**当て推量ではなく手元の鍵素材との比較**である。

  黙って壊れはしない。全経路が投げる**（§4.2 の `packing.json` は `days` も `events` も
  持たないので `validateEvents` を通らない）── `saveLocal` は `:235` で、
  `publish` は `:309` で、`adoptRemote` は `:246` で、`load` はリモートを検査する `:170` で
  投げる。`sync.js` は**検証してから書く**順序なので、この段階では旅程の下書きは無傷。
  `load()` の下書き棄却（`:141-151` → `:182` の `if (!draftRejected)`）も
  `storeAdopted()` を飛ばす動き、つまり上書きを**防ぐ**側であって、失う側ではない。

  **危ないのは部分的に直したときで、そこが本当の罠。** 「検証器を注入すればいい」と
  気付いて検証器だけを `config` へ出すと、持ち物の下書きが自分の検証を通るようになり、
  **そこで初めて `saveLocal` が `store.write(DRAFT_KEY, …)` に到達して
  `tp:events` を持ち物データで上書きする。旅程の未公開の編集はこの瞬間に消える**
  （持ち物側で `publish()` まで進めば `storeAdopted()` が `tp:events-base` も塗り替える）。
  人が気付くのは次に旅程ページを開いたときで、`load()` が「旅程の形になっていない」と
  警告して手元の下書きを捨て、リモートの内容に戻る ── 棄却は損失が起きた場所ではなく、
  損失が見えた場所にすぎない。

  **直し方: `config` に保存キーの接頭辞と検証器の両方を足し、既定を今の値
  （`events` / `events-base` / `validateEvents`）にする。コミットメッセージの組み立ても
  ファイルごとに差し替えられるようにする。3 つを一度に直すこと** ──
  どれか 1 つだけを注入可能にすると上の静かなデータ消失が生まれる。

  **B4 で `codec` が 4 つ目の注入口として加わるので、B4 でまとめて直す**（2026-08-10 決定、
  §5.1）。危険の性質は変わらない ── 5 つのうち一部だけを注入可能にすると同じ消失が起きる。
  当初は「B2 で 2 つ目の `createSync` を作る前に必ず直す」としていたが、B4 が先に
  `sync.js` へ手を入れるため前倒しになった。

  **2026-08-10（Phase B2）追記: `noun` が 6 つ目の注入口として加わり、6 つになった。**
  経緯と、なぜ表示専用の項目まで同じ「揃えて渡す」組に入れたかは次の項目を参照。
  同じ B2 で `createPublishUI()` 側の同型の依存も見つかって解消しており、
  あわせてその次の項目に記録する。

- **`createPublishUI()` も旅程専用だった（B2 で発見・解消）。** 上の `createSync()` と
  同じ形の依存が `publish-ui.js` にも残っていた:

  1. **検証器** — `validateEvents` を module top で import し、`doPublish()` が
     直に呼んでいた
  2. **文言** — `MESSAGES` の複数の文字列（`offline` / `remoteIsNewer` ほか）に
     「旅程」が埋め込まれていた

  そのまま持ち物ページで使い回すと、持ち物データが `validateEvents` に落ちて
  **公開ボタンが必ず失敗する**か、通知が「最新の旅程を確認できませんでした」と
  開いてもいないページの話をする。

  **直し方: `createPublishUI({ …, content: { validate, noun } })` として、
  `validate` と `noun` を必須の組で受け取ること**（`assets/js/publish-ui.js`。
  `content` が無い、または `validate` / `noun` のどちらかが欠けていれば
  `createPublishUI()` はその場で `Error` を投げる）。

  **`validate` と `noun` を別々の任意引数にせず、組を必須にした理由**:
  別々にすると「片方だけ渡して、もう片方は既定値（旅程）に落ちる」呼び出しが書ける。
  `noun` だけ渡して `validate` が既定の `validateEvents` に落ちれば、持ち物データが
  旅程の検証に掛かって公開ボタンが必ず失敗する。逆に `validate` だけ渡して `noun` が
  既定の「旅程」に落ちれば、持ち物ページの通知が「最新の旅程を確認できませんでした」と
  出す。組を必須にすれば、どちらの片手落ちも `createPublishUI()` を呼んだ時点で
  `Error` として即座に落ちる。

  **危険の性質は `createSync()` の項目とは違う。** こちらは呼び出しの時点で
  **必ず投げる**ので、静かにデータが消える `createSync()` の罠より発見は速い。
  同じ形の問題（「旅程専用の依存が注入の外にある」）が 2 か所にあったという点は
  同じでも、失敗の壊れ方（黙って消えるか、必ず落ちて気付けるか）は同列に扱わないこと。

- **`sync.js` の注入項目が 6 つになった（B2 で `noun` を追加）。** `draftKey` /
  `baseKey` / `validate` / `commitMessage` / `codec` の 5 つに、画面の文言で使う名詞
  （「最新の◯◯を確認できませんでした」の◯◯）として `noun` を加えた。`noun` は
  表示専用で、取り違えても `store.write()` の宛先も `validate` の経路も変わらない ──
  上の `createSync()` の項目が指す**データ消失の危険はここには無い**。

  **それでも同じ「6 つ揃えて渡す」組に入れた理由**: 揃えて渡す対象を「危険なものだけ」に
  絞ると、新しい設定を足すたびに「これは危険な側か、表示だけの側か」を誰かが
  毎回判定し直す必要が生じる。判定を間違えれば結局同じ罠を踏む。危険度で場合分けする
  ルールより、「config は全部揃えて渡す」という 1 つのルールのほうが覚えていられて、
  実際に守られる（`assets/js/sync.js` の `DEFAULT_CONFIG` のコメントも同じ判断を書いている）。
- **時計ずれで他端末の公開を黙って上書きしうる（残存リスク）。**
  `tp:events-base` に入る `updatedAt` は公開した端末の時計で押される。押す端末が
  複数あるので順序関係は保たれない ── A の時計が遅れていれば、A があとから公開した版の
  `updatedAt` が B の版より古くなり、B の端末の base を下回る。`assertRemoteNotAhead()` は
  「リモートは進んでいない」と判断し、A の公開を上書きする。
  免疫を付けるには内容のハッシュか sha が要るが、読み込みはトークン無しの素の `fetch`
  なので sha が手に入らない（トークンを持たない端末でも旅程を開けるようにするための選択）。
  上書きしてもコミットは git 履歴に残るので復旧はできる。
  `assets/js/sync.js` の `BASE_KEY` のコメントがこの節を指している。

  **これは公開側（リモートが上書きされる）の話で、受け入れている理由は
  「git 履歴から戻せる」こと。** 同じ時計ずれが起動時の判断
  （`decideSync()`）に及ぶと**手元の下書きが消える**という別の被害になり、
  そちらは git 履歴に控えが無いので受け入れられない ── B1 の最終レビューで
  Critical として直してある（上の「最終レビューで見つけて直した項目」）。
  **2 つを同じ残存リスクとして扱わないこと**
- **保存領域に書けない端末（プライベートブラウジング、容量超過）では公開が毎回 409 になる。**
  base を残せないため。`publish-ui.js` は「取り込んでから公開し直す」という成立しない
  案内を出さないよう文言を分けてあるが（`MESSAGES.cannotPersist`）、根治していない。
  直すなら「公開が成功した直後に限り base が無くても通す」を sync 層に入れる
- **壊れた下書きを拒否した回は base を更新しない。** 救出できる中身を上書きしないための
  判断だが、次の公開は必ず 409 になる（「取り込む」を押せば済むが、その端末の編集は失われる）
- **`canPersist()` の書き込みプローブは 1 バイト。** 容量ぎりぎりの端末では
  プローブだけ通って本番の書き込みが失敗しうる（失敗自体は画面に出る）
- **`storeAdopted()` は途中まで書けたときに画面と保存領域がずれる。** 下書き → base の
  順に書くので（この順である理由は同関数のコメント参照）、base の書き込みだけ失敗すると
  `adoptRemote()` が投げ、`publish-ui` は「取り込めませんでした」と出し、
  `onAdopt` を呼ばないまま終わる ── **保存領域にはリモートが入っているのに画面は
  古いまま**で、次の編集がその古い内容を保存し直して取り込みを黙って巻き戻す。
  base は 30 バイト程度の文字列なのでここだけ失敗する状況は極めて狭いが、
  順序の非対称性が書かれていないのは片手落ち
- **一度押した「取り込む」ボタンは構えたまま戻らない。** `publish-ui.js` の同期バーの
  ボタンは 1 度目で身構え 2 度目で実行するが、トークン削除ボタンと違って
  `updatePanel()` に相当する解除の経路がない。ラベルが変わるので状態は見えており、
  害は「押しっぱなしに見える」だけ
- **`sync.load()` が投げるとトークン設定への導線も出ない（B4 で解消。ただし
  残った穴があるので節から削除はしない — 下記参照）。** `publish-ui` は読み込みの
  あとに組み立てていたため（`schedule.js` の `main()` は `await sync.load()` の
  あとで `createPublishUI()` を呼んでいた）。リモートの `days` / `events` が壊れていると
  `sync.js` の `load()` がリモートを検証するところで `validateEvents` が投げ、
  `main()` の `catch` がそのまま再送出して落ちていた ── 公開ボタンもトークン設定も
  DOM に現れず、この状態をブラウザから直す手段が無かった。

  **2026-08-10: B4 で解消した。** `schedule.js` の起動順を「鍵の確認 →
  `publish-ui` の組み立て（DOM への挿入込み）→ `sync.load()`」に変え、
  `publish-ui.js` の DOM への挿入を `start()` から `createPublishUI()` 本体の末尾へ
  移した。`sync.readDraft()` が検証を通った下書きを返すので、それを `state` に
  載せれば、リモートが壊れていても手元に正しい下書きを持つ端末では実際に
  公開ボタンが押せる（`events.json` の手編集を廃止した以上、これが唯一の
  復旧手段になったため — §6.5）。

  **ただし完全には塞がっていない。** 壊れたリモートが「JSON としては読めて
  `updatedAt` が `tp:events-base` より新しい」形だと、`assertRemoteNotAhead()` が
  PUT の前に 409 で止める。409 の画面が示す唯一の逃げ道（「取り込む」→
  `adoptRemote()`）も `validate` で落ちるので、その端末では直せない。この場合の
  復旧はリポジトリへの git コミットに戻る。直すなら「リモートが検証を通らないと
  分かっている回に限り突き合わせを飛ばす」を sync 層に入れることになる
  （B4 の範囲では直さないと決めた。直すには 409 の判断そのものを設計し直す
  必要がある。Task 5 のレビューで発見、2026-08-10）。

  なお `sync.js` の `assertRemoteNotAhead()` が突き合わせを省いて公開を通すのは
  **これとは別の壊れ方**（`validateEvents` を通るが `updatedAt` だけ読めない）に対する
  措置で、そちらはページが開くので公開が実際に復旧手段になる。**この 2 つの
  壊れ方を混同しないこと**（`sync.js` の同関数のコメントも区別して書いてある。
  以前は区別せず「公開こそが復旧手段になる」と書いていたが、それは前者の
  壊れ方には当てはまらない）
- **`StoreWriteError` で終わった公開はコミット URL を出せない。** URL を得たあと
  `storeAdopted()` で投げるため。リンクの代わりにリポジトリを見てもらうしかない
- **公開ボタンに件数を出せない。** base に持っているのは時刻だけで内容がないため、
  何件変わったかを算出できない。出すなら取り込んだ本文を 3 つ目のキーに持つ必要がある
